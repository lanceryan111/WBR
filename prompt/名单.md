- **配置仓库**：把环境配置打包成制品，再由应用部署流程引用。

这些是截图中另一段 AI 回答的描述，**还需要用实际文件验证**。另外，截图展示的是“应用 + 配置”两个仓库，而你说的两个新 repo 也可能是“两个独立 API”。这一点务必在提示词里说清楚，否则 Copilot 可能从一开始就建错关系。

### 1. 先让 Copilot 真正能读到相关仓库

建议在同一个 VS Code workspace 中准备：

| 仓库 | 用途 |
|---|---|
| 旧应用 repo | 参考原有应用构建、部署行为 |
| 旧配置 repo | 参考配置制品如何生成和消费 |
| 新版 CI/CD solution repo | 确定新接口、必填参数、工作流调用方式 |
| 新 repo A | 需要生成配置的目标 |
| 新 repo B | 需要生成配置的目标 |

选择能搜索、读取文件和修改文件的 Agent 模式。明确附加关键文件，例如工作流、`CI.yml`、`CD.yml`、`pom.xml`、配置打包描述文件，以及新版方案里的示例和被调用工作流。

**文件夹在 workspace 里，不代表每个文件都已经被模型读过。** VS Code 官方说明，Copilot 通过搜索和文件读取工具获取相关上下文，所以提示词要要求它报告实际读取的文件和证据。[官方说明](https://code.visualstudio.com/docs/agents/reference/workspace-context)

### 2. 第一轮：分析接口和差异，暂不生成 pipeline

把下面的占位符替换为真实路径。新版 solution 最好指定你们准备采用的 tag 或 commit，避免分析时版本漂移。

我要为两个新仓库接入新版 CI/CD solution。请先分析实际仓库，建立有文件证据的迁移方案；本轮不要修改 pipeline。

仓库：
- OLD_APP：<旧应用 repo 路径>
- OLD_CONFIG：<旧配置 repo 路径>
- NEW_SOLUTION：<新版 CI/CD solution repo 路径>
- 目标 solution 版本：<tag / commit>
- TARGET_A：<新 repo A 路径>
- TARGET_B：<新 repo B 路径>

TARGET_A 与 TARGET_B 的关系：
<明确填写：两个独立 API；或一个应用 repo 和一个配套配置 repo。如果各 API 另有配置 repo，也列出路径。>

目标环境：dev。本轮不扩展到其他环境。

证据规则：
- 新版 solution 的实际实现及其接口定义是接入依据，文档和示例用于辅助核对。
- 旧仓库只用于理解旧流程及业务需求，不能直接认定旧参数在新版仍然有效。
- 新服务的构建方式、模块、制品名和部署需求必须以目标仓库为准。
- 文档、示例和实现冲突时，指出冲突及影响。
- 每个关键结论提供 repo、文件路径和相关行号。
- 区分已确认事实、推断和缺失信息。无法读取的文件不得声称已分析。
- 不输出 secret 的值。

请按以下顺序分析：
1. 确认所有仓库可访问，列出各自职责、当前版本和已读取的关键文件。
2. 追踪旧流程：触发器 → 调用工作流 → 构建/测试 → 发布应用或配置制品 → 部署时消费制品 → 启动和健康检查。
3. 追踪新版 solution 的入口及其调用链，包括 reusable workflows、actions、脚本和配置解析代码。对工作区外不可访问的依赖明确标记。
4. 提取新版接口：inputs、类型、默认值、必填项、secrets 名称、permissions、runner、配置 schema、输出、制品命名和版本规则。
5. 核对两个目标仓库与旧例子的差异：JDK、Maven 模块、打包方式、应用名、制品坐标、配置来源、部署目标、启动方式和健康检查。
6. 检查新版方案是否支持目标仓库实际需要的部署方式，不要仅凭存在 Dockerfile 就认定使用容器部署。

输出：
- 旧流程与新版流程的简要调用链。
- 迁移映射表：旧配置项 → 新版配置项 → TARGET_A 值 → TARGET_B 值 → 文件证据 → 是否待确认。
- 各目标仓库需要新增或修改的文件清单。
- 会阻塞生成可运行 pipeline 的缺失信息。

可以从文件查到的信息请自行查找；只有文件无法确定的关键值才询问我。不要用通用 CI/CD 模板替代仓库分析。

**这一轮最值得检查的是迁移映射表。** 如果它无法明确说明“新版工作流接受什么输入、配置制品怎么传到部署阶段”，这时继续生成 YAML 往往只会放大错误。

### 3. 第二轮：基于确认的接口直接生成文件

第一轮中的关键缺失信息补齐后，再发：

补充信息与已确认决定：
<填写上一轮缺失的参数及确认结果>

实施要求：

2. 遵循指定版本 NEW_SOLUTION 的真实调用方式、文件结构和配置 schema。
3. 分别使用两个目标仓库自己的应用名、模块、制品坐标、配置引用及部署参数，不要简单复制后只替换 repo 名。
4. 明确应用制品与配置制品的生产者、消费者、版本选择和发布顺序；说明如何避免部署到不匹配的版本。

8. 优先复用新版 solution 的能力；不要自行重写其已有的构建或部署逻辑。
9. 不 push、不触发远程 workflow、不发布制品、不执行部署。

- 说明每项变更对应哪个新版接口及其文件证据。
- 列出 GitHub 侧需要配置的变量名、secret 名、环境、权限或其他前置条件。
- 给出从配置制品发布到应用 dev 部署的执行顺序。

### 4. 第三轮：让它检查跨文件契约，而不只是 YAML 语法

请重新读取生成后的文件和指定版本 NEW_SOLUTION 的实际实现，进行一次 CI/CD 接入审查。不要直接沿用上一轮结论。

逐项检查：
- 每个调用的 workflow 路径和 ref 是否有依据；inputs 名称、类型、必填项及 secrets 是否匹配。
- permissions、runner 和环境配置是否符合调用链要求。
- CI 输出的应用/配置制品名称、坐标和版本，是否与 CD 下载和解包逻辑一致。
- 配置包目录结构是否与部署脚本预期一致。
- 两个目标仓库之间是否混用了应用名、模块名、制品路径或部署参数。
- 是否遗留旧项目的值，或误用了旧版 solution 的参数。
- 触发条件、分支和事件上下文是否符合 dev 流程。
- 启动、健康检查和失败处理是否有实际实现依据。

执行当前环境支持的本地静态检查和必要构建检查，优先使用仓库已有检查工具。不要执行发布或部署命令。

对发现的问题，提供严重程度、文件位置、失败原因并修复可确定的问题。

最后分别报告：
1. 已通过的检查及证据。
2. 因工具、权限或依赖不可用而未执行的检查。
3. 必须通过首次远程 CI/CD 运行验证的事项。

不要把 YAML 可解析或本地检查通过描述为部署成功。
