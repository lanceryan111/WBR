这个 Skill 学到的“你的风格”

它会默认把你定位成 Senior / Lead Platform Engineer 的沟通方式，而不是普通的 corporate English assistant。

例如你经常遇到的这种情况：

We don’t own this app. Is it better for app owner to provide this information?

Skill 不会简单润色成：

We don’t own this application. Please contact the application owner.

而会倾向于：

We don’t own this application, so I think the app owner would be better positioned to confirm the application-specific requirements. I can provide the platform-side details if needed.

这就是我们之前经常帮你调整出来的模式：

事实 → ownership boundary → authoritative owner → 我可以提供什么帮助

而不是甩锅。

它也专门加入了你非常常见的场景：

technical clarification、ownership boundary、manager status update、dependency/blocker、follow-up、request、apology、meeting coverage、thank-you、cross-team coordination、submitted vs completed、technical uncertainty。

在 M365 Copilot 里面怎么装

目前比较适合你的不是自己开发一个完整 custom engine，而是创建一个 Declarative Agent。Microsoft 现在的 Agent Builder 本身就是通过 Instructions + Knowledge + Starter Prompts 来定制 Copilot 行为。

在电脑上的 Microsoft 365 Copilot：

New agent → Skip to configure

Name 可以用：

Workplace Communication Copilot

Description：

Drafts and optimizes concise, professional Outlook emails and Teams messages for technical, project, and cross-team communication in a senior Platform/DevOps engineering voice.

然后打开我给你的：

agent-instructions.md

全部复制到 Instructions。

接着把：

communication-style-examples.md

上传到 Knowledge。

Agent Builder 目前支持上传文件作为 embedded knowledge，也可以使用 SharePoint、OneDrive、Teams chat、Outlook email 等作为 knowledge source，具体能力还取决于你们公司的 Microsoft 365 配置。

Microsoft 官方也特别建议：行为规则应该留在 Instructions，而不是为了绕过 8,000 字限制把 instructions 塞进 SharePoint knowledge。 Knowledge 更适合事实和示例。

所以我这次已经按照这个 architecture 给你拆好了。

以后实际怎么用

以后你甚至不需要写很完整的 prompt。

例如：

Teams: ask Manny to attend the meeting while I’m away and give me an update afterward

它应该直接生成适合 Teams 的短消息。

或者：

Email: Shriram document shows AD group complete but ticket actually still pending. Ask him to double check.

它会自动应用：

不指责 → 区分 submitted/completed → clear ask

再比如：

Manager update: iOS CI done, resigning integrated as interim solution, Android next, waiting for access.

它会自动切换成：

current state → outcome → dependency → next step

而不是给 Marcin 发一大堆 implementation details。

你还可以直接覆盖默认风格：

more technical

more concise

executive-friendly

slightly more casual

firmer but still professional

less formal

这个对你尤其有用，因为你给 Manny、Marcin、developer、project stakeholder 发消息时，语气实际上是不一样的。

我最建议你下一步做的事情

现在这个版本我认为可以叫 v1.0。

真正让它越来越像你的关键，不是继续往 prompt 里面疯狂加规则，而是建立一个：

Context → AI Draft → 你最后真正发出去的版本 → 为什么改

的 feedback dataset。

比如以后 Copilot 给你：

We require the application team to confirm…

你实际改成：

I think the app owner would be better positioned to confirm…

那就记录下来。

如果类似修改出现 3 次以上，我们再把它抽象成新的 rule。

这样你的 Skill 会慢慢从：

Generic Senior Engineer Writing

变成：

你的个人 Workplace Communication Model

而且 Microsoft Agent Builder 本身也支持在创建后继续调整 Instructions、Knowledge 和 Starter Prompts，并通过 Try it 测试。
